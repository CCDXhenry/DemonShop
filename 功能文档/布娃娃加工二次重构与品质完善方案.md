# DemonShop 布娃娃加工二次重构与品质完善方案

> 编写日期：2026-11-13  
> 用途：供后续新任务接手，梳理当前原型的不足，明确重构顺序、体验目标、工程边界和验收方式。  
> 当前结论：现有版本已建立流程规则原型，尚未达到可交付的完整体验标准。不能以 strict、断言数量或辅助脚本跑通流程，替代手感、视觉和连续游玩的验收。  
> 本文仅提供方案与交接信息，不表示下列改进已经实现。

## 1. 已确定的产品目标与边界

核心循环保持为：

**街道生成白膜 NPC → 武器击晕 → 肩扛搬运 → 存放池或直接上桌 → 身体涂画画符 → 祭坛转化 → 药水架取药 → 召唤法阵提交 → 获得金币。**

已由用户确定，后续任务不得擅自更改的规则：

- R15 白膜 NPC 正常行走，累计多次命中后全身物理晕倒，不自动苏醒。
- 多人完全共享合作；搬运和画符期间独占，释放后其他玩家可接手。
- 一次肩扛一具；工作台允许直接调取共享池库存，也允许亲自搬上桌。
- 画符采用身体表面覆盖率，重复涂同一区域不增加进度。
- 固定紫色发光笔迹；有效拖画同时驱动身体旋转，不能擅自改成右键单独旋转。
- 可涂身体表面覆盖 70%，对应 HUD 进度 100%。
- 退出画符、死亡或掉线后，保留本局身体及画符进度；释放操作占用供其他玩家接手。
- 药水可由任何玩家接续搬运，最终提交者获得金币。
- 金币沿用当前 `PlayerInfo` DataStore；没有旧项目数据迁移需求。身体、笔迹、工位与药水仅在当前服务器有效。
- 支持键鼠和触屏；已有用户授权记录包含单人、双人 Studio Play 验收，接手时仍须核对新任务的最新授权及项目规则。

原定基础数值先保留，体验调优时单独记录调整理由：

| 参数 | 当前值 |
| --- | --- |
| 街道 NPC 配额 | 6 具，未搬走的晕倒 NPC 也占配额 |
| 捕获后补充间隔 | 5 秒 |
| 击晕次数 / 攻击间隔 / 距离 | 3 次 / 0.6 秒 / 7 studs |
| 工位与物品交互距离 | 8 studs |
| 存放池 / 药水架容量 | 各 8 |
| 祭坛容量 / 转化时间 | 1 具 / 10 秒 |
| 每瓶奖励 / 初始金币 | 100 / 0 |

当前实现另外加入了身体总数 32、每面 8×8 覆盖单元、笔刷半径 0.32 studs、最短有效画符累计时间 12 秒等工程默认值。这些并非用户逐项确认的产品规则，应在二次重构中复核。尤其不能用最后卡在 99% 的表现掩盖时间门槛。

## 2. 现状复盘：为什么目前显得粗糙

### 2.1 已核实的实现事实

| 子系统 | 当前实现 | 对品质的影响及后续工作 |
| --- | --- | --- |
| 白膜 NPC | 由默认 R15 生成后改为块状身体，简单随机 MoveTo；越界时直接重新定位 | 缺少有设计的外形、停走节奏、避障与越界恢复表现；应保留白膜定位，但完成比例和动作设计 |
| 攻击 | 按附近目标、方向、距离和版本判定；客户端用 Tool.Grip 短暂改变表现 | 挥击、接触点与伤害时刻没有完整动画契约；必须让玩家看得懂是否打中 |
| 布娃娃 | 14 个 BallSocketConstraint，按少量关节名称设置限位；同一碰撞组整体互不碰撞 | 已有基本物理骨架，尚缺逐关节调校、肢体接触策略及多种倒地姿态验证 |
| 肩扛 | 将身体复位后按固定偏移摆在角色旁，再焊接躯干；搬运时整体关闭身体碰撞 | 功能可用，但缺少抓起、扛起、持握与放下的动作衔接；需实测身体是否真正落在肩上、是否遮挡镜头或穿墙 |
| 存放池 | 将身体切到固定静态姿态后按槽位排放 | 看起来更像物品摆放；缺少入池、取出与占位反馈，不应直接把稳定摆放等同于完成表现 |
| 工作台 | 固定镜头、身体悬空、持有画笔 Tool；进入退出以直接切换为主 | 缺少完整镜头过渡、笔尖反馈、画笔与输入的对应以及完工反馈 |
| 笔迹 | 每个外露面 8×8 覆盖格；每个已覆盖格克隆圆角 Frame 到 SurfaceGui | 格子与圆点直接承担视觉笔迹，线条精细度、连贯性、跨面衔接和实例规模都有明显上限 |
| 涂画旋转 | 输入位移直接累加 yaw/pitch；客户端逐帧 PivotTo，服务端处理采样时也 PivotTo 同一身体 | 展示姿态和权威判定耦合；需重构预测、采样所对应的姿态以及其他观察者的平滑表现 |
| 进度判定 | 计算覆盖面积，同时要求累计有效会话时间；时间不足时显示 99% | 容易产生“已经涂够却没完成”的不透明感受；时间门槛应作为安全校验处理或明确反馈 |
| 工位流程 | 通用交互按钮配合最近目标；提示主要是文字与库存/CD | 缺少具体操作预览、清楚的占用反馈及世界内引导；新玩家容易不知道下一步 |
| 药水与奖励 | 简单药水模型，CD 完成后出现在架上；提交后文字提示加金币 | 缺少可识别的加工完成、出货、取药、献祭与金币到账反馈 |
| 同步 | Changed 通知全量快照；客户端每 3 秒请求 Sync，附带补发笔迹 | 当前同步偏重，且正常刷新与异常修复没有清楚分离；画符高频数据不应反复带动全局状态广播 |
| 代码职责 | ServerGameManager 同时包含玩家存档生命周期、NPC 调度、工位、画符、奖励和同步；客户端总控也较集中 | 当前总控已分别约 850 行、560 行，后续继续往其中追加品质代码会增加维护和回归成本 |

上述是源码核实后的结构问题与品质风险，不代表所有问题都已在实机中稳定复现。后续任务必须先观察，再将问题归类为“已复现”“代码风险”或“体验决策”。

### 2.2 既有验证的真实边界

已有记录包括：18 个改动文件 strict 无错误、38 条离线规则断言、25 条隔离 Play 状态机断言、单人启动、双人交接、金币保存重进，以及模拟器 Touch 输入留下笔迹。

但上一轮流程验收中使用过服务端定位、临时固定测试角色、正式网络请求驱动和自动表面扫涂。因此只能说明部分规则、状态流和同步能够工作，**不能证明玩家从出生开始，不借助开发工具就能自然走完一轮**。

尚不能作为已通过项目交付标准的内容：

- 不瞬移、不直接调用加工函数、不自动扫涂的完整玩家流程。
- 真实击打接触感、反复抓放、肩扛上下楼、转弯、经过门洞的连续表现。
- 普通玩家依靠提示理解目标、读懂画符进度并完成身体各面的涂画。
- 完整真实触屏拖画手感、实体手机性能、长时间压力与高延迟网络。
- 连续完成多轮后物品、UI、画笔、相机、连接和缓存均无残留。

共享 Core/TeleportTool 的两条既有 strict 诊断仍应与本业务诊断分开报告，不能为清空全量结果擅改共享库。

## 3. 重构原则与验收组织

1. 优先做可体验的布娃娃与画符样板，得到用户认可后再扩展到整套流程。不能先批量堆积 UI、VFX 与新机制。
2. 游戏规则和表现分层：服务端拥有物品、占用、覆盖率、产出及奖励；客户端负责即时输入、镜头、动画、笔迹与提示。
3. 展示精度与覆盖判定精度分开；提高画符品质不能简单等于增加格子数和 GUI 实例数。
4. 所有重要反馈都有明确开始、成功、失败和取消状态；取消、死亡与掉线共用清理路径。
5. 采用玩家视角验收。辅助脚本用于定位规则问题、构造边界场景，单独记录，不能代替体验录像。
6. 每阶段交付可评审的小样、实际检查结果和未解决问题。未经确认的美术及手感选择单独列出。

本轮完善范围保持在现有循环：不恢复旧养殖、商业化、成长商店，不新增品质、稀有度、配方、顾客、技能树等系统。

## 4. 分阶段实施方案

### 阶段 A：接手核查与体验基线

**目标：明确真实问题，保存可对比的当前状态。**

- 读取 AGENTS.md 与项目 skill；检查当前 Git diff、Script Sync、Place1 连接和现有修改归属，不覆盖用户后续工作。
- 核对本地源码与 Studio 编辑缓冲区，同时区分编辑缓冲区、已保存 Source 与本地资源导出。上次核对 22/22 一致，其中 18 个脚本存在编辑缓冲差异；这不是新任务开始时的实时结果。
- 在允许的 Play 环境按正常玩家操作完整体验一轮，记录每个阻断点、误操作、镜头切换、物理异常和反馈缺失。
- 保存关键视角基线：街道、击晕、肩扛、上桌、涂画、转化、取药、提交。
- 记录空场景及加工过程的帧时间、物品与约束数量、笔迹实例数量、网络消息量，作为后续比较基线。

**交付：**按优先级整理的问题清单；每项附复现步骤、预期和实际结果。没有实际复现的项目保留为待验证风险。

### 阶段 B：布娃娃、战斗与搬运样板（最高优先级）

**目标：先让一具 NPC 的“打倒—扛起—搬走—放下”可信、稳定、好操作。**

- 白膜造型保留 R15 契约，统一身体比例、朝向、碰撞代理与抓取锚点；不使用临时生成时的偶然偏移作为持握位置。
- 将关节参数独立成配置，按颈、肩、肘、腕、腰、髋、膝、踝分别设计范围与阻尼；验证弯折方向。
- 明确 Walking、Stunned、Carried、Stored、Workbench、Converting 等物理表现配置；业务加工阶段与物理姿态分别记录。
- 按邻接关系屏蔽必要的自碰撞，明确身体对其他身体、玩家、地面和墙体的策略。避免依靠整体无碰撞掩盖穿模，也避免让所有细小肢体无限推挤。
- 行走转晕倒时保留合理的当前姿势与有限速度；命中方向可带来受控反应，不能造成甩飞。
- 加入简洁完整的棍棒挥击：前摇、命中窗口、收招与冷却。使用与挥击相符的服务端空间检测，保留一击只影响一具的基础规则。
- 搬运采用可配置的肩部/手部锚点和持握姿势；身体承载位置稳定，四肢保留受控摆动。抓起与放下先做过渡，结束后再切换稳定物理状态。
- 处理不同玩家体型；验证角色移动、转向、跳跃、楼梯、门洞和相机缩放。先确定肩扛样板，再推广到其他道具。

**验收：**同一具 NPC 连续抓放至少 20 次；连续肩扛通过楼梯和自动门；无散架、持续抖动、明显穿身、异常速度或残留焊接。双方观察结果一致。提供玩家视角对比材料。

### 阶段 C：工作台与连续笔迹样板（与阶段 B 同级重要）

**目标：让画符成为明确、可控的核心操作，而不是给身体格子填色。**

#### 工作台演出与画笔反馈

- 工作台完整状态为待放置、放置过渡、可操作、绘制中、完成演出、可取走；镜头进入和退出有短过渡。
- 模型保持屏幕中心，尺寸与相机距离按身体包围盒确定；头、手和脚都要可操作，HUD 不遮挡主要身体区域。
- 明确画笔的世界内持握表现与屏幕笔尖指示的关系；笔尖位置、接触反馈和笔迹落点一致。
- 保留“拖画同时旋转”。旋转采用有界、按时间平滑的角速度，缓入缓出；对指针轻微抖动设置死区，松手及时停止。
- 禁止客户端与服务端同时逐帧争写同一个权威物理实体。优先采用当前操作者的本地展示副本，服务端保留工位实体及会话姿态；其他玩家看到经过同步和平滑的工位展示。

#### 笔迹与覆盖率分离

- 服务端维护覆盖数据；客户端使用独立的连续笔划数据与渲染器。覆盖单元只用于统计，不直接作为最终画面。
- 针对当前块状白膜，先做按身体局部面坐标生成连续线段的 PoC：同面插值，跨面断点按实际边界连接或分段，笔迹跟随部位变换。
- 第一版渲染优先评估可复用的薄片/线段模型模板；需要纹理画布等方案时，先验证 API 可用性、权限、内存和目标设备，再决定替换方式。不能未经验证直接绑定方案。
- 笔划应有稳定宽度、圆润端点和统一紫色发光效果；不能穿透身体，也不能沿移动方向漂浮或跳到背面。
- 覆盖率使用面积加权、隐藏接触面遮罩、插值与去重。提高分辨率前先校准笔刷面积和可达性；遮罩生成与运行时使用同一版本参数。
- 完成条件主要由覆盖率决定。现有 12 秒条件需复核：若只用于反作弊，不应在合法覆盖已完成后让 UI 无说明地停在 99%。
- 笔迹渲染设定明确的单体与同服预算，支持线段合并、按可见范围加载及对象回收；不能为提高精细度无限克隆 GUI 或 Part。

**验收：**真实鼠标和真实模拟触屏拖画均可完成；重复涂同处不刷进度，跨躯干和四肢的线条可读；旋转不丢笔迹、不中断落点；退出后另一人能从相同进度继续。最终完成过程必须由人工输入完成一次，禁止用扫涂脚本代替。

### 阶段 D：工位衔接、药水与奖励表现

**目标：玩家在世界中能理解材料去了哪里、当前是什么状态、下一步做什么。**

- 为池的投放、取出，桌的放置、操作、取走，祭坛的投入和药水的领取设置明确锚点与可见反馈。
- 存放池保留稳定槽位，但加入短暂入池、安置与取出过渡；满容量和空库存时有清楚反馈。
- 工作台直接调用池库存时，表现出材料从池中到桌面的过程；短时间内保留工位占用，避免状态与视觉分离造成重复操作。
- 祭坛明确区分转化中、完成待出货、架满阻塞；完成后只消费一次身体、产出一次药水。
- 药水完成白膜品质下的识别设计：瓶体、封口、内部发光主体和持握姿态。出货与取药要能分辨。
- 法阵使用显式交付锚点，校验距离与视线；提交演出包含药水消耗、法阵响应和金币到账。奖励仍由服务端一次性结算。
- 新特效、动画和音频以这套流程为触发来源，明确取消与释放点；优先少量、准确的反馈，不堆叠闪光、音效或弹窗。

**验收：**无需开发者口头指路，玩家能区分各工位状态并完成材料流转。两人可自然交接；占用、满库存、错误材料和中断都不丢物品、不复制产出。

### 阶段 E：HUD、引导与多端输入

**目标：普通 HUD 简洁，操作提示准确，触屏不会被系统区和手指遮挡。**

- 在现有霓虹场景中统一界面的层级、留白、字体、色彩和反馈；先做 HUD 与画符界面两张样板，经用户确认后铺开。
- 普通 HUD 继续固定 1920×1080 Center 画布，动态单行文本二分拟合，描边使用 ScaledSize。
- 触屏操作保留独立模板，并按目标设备验证物理触控尺寸。普通 HUD 不随输入设备随意重排。
- 使用有意义的操作文案，如“存入身体”“从池中取出”“开始画符”“取走完成身体”；触屏不直接照搬 E/Q 键位文字。
- 目标选择加入可见性与当前动作资格检查，提供适度目标锁定，避免仅按最近距离在相邻物品和工位之间跳动。
- 给出简短下一步引导，可按玩家当前携带物、附近工位和加工阶段变化；不做冗长教程弹窗。
- 画符界面突出模型、进度和少量必要操作；完成、取消与被占用状态可清楚分辨。

**验收：**桌面、手机横屏和竖屏均可操作；主要文本不溢出，按钮不压住原生移动控件；画符退出后相机、摇杆、跳跃和武器状态都正常恢复。

### 阶段 F：职责拆分、同步与长期稳定性

**目标：使品质迭代有清楚的归属，避免总控持续膨胀。此阶段与 B/C 的改动同步推进，不另造通用引擎。**

建议服务端职责：

| 职责 | 管理内容 |
| --- | --- |
| GameCoordinator | 只负责装配、启动顺序、关闭与系统间协调 |
| BodyService / RagdollController | 身体实例、关节、物理模式与销毁 |
| NPCService / CombatService | 生成、闲逛、命中与击晕 |
| CarryService | 单槽搬运、占用、抓放及异常回收 |
| StationService | 池、桌、祭坛与药水架的物品转移和事务边界 |
| RuneService | 画符会话、姿态校验、笔划与覆盖率 |
| PlayerProfileService | 玩家加载、金币、租约、保存与释放 |
| ReplicationService | 首次快照、增量通知、笔划补发及重新同步 |

客户端按输入、目标选择、画符会话、笔迹渲染、镜头、HUD 与工位表现拆分。共享层只保留类型、配置、协议及可独立测试的纯规则。

关键接口要求：

- 物品以唯一 ID 为主键，类型和状态使用明确联合类型或集中契约；模型引用由实例映射维护，不能成为全部业务状态的载体。
- 操作请求包含请求标识、目标 ID、预期版本；失败返回明确原因，客户端能区分过期、占用、距离、容量和材料错误。
- 画符请求带会话 ID、递增序号、采样对应姿态与局部坐标；旧会话、重复批次及不可达采样不参与结算。
- 可靠事件承担物品转移、产出、完成和金币结算；高频纯展示数据与关键结算分开。
- 首次进入及确需修复时发送完整快照；正常使用增量更新。替换常态每 3 秒全量 Sync，笔迹补发应有分块、去重与预算。
- 客户端即时显示本地笔划，接收服务端确认后合并；拒绝时有明确回退，不能把等待往返网络的延迟直接暴露成落笔迟滞。
- 所有连接、动画轨道、任务、模板克隆、对象池、相机和输入锁必须有所有者与释放点。

迁移顺序：先锁定现有规则测试和协议，再迁移单一职责及调用方；每完成一块就清理旧路径。避免一轮内同时重写全部规则、网络、UI 和资源。

**验收：**双人同时操作不复制物品；晚加入能恢复工位和笔迹；旧请求不回滚新状态；循环创建销毁后实例与连接数量回落；金币继续沿用 PlayerInfo 并保持读取失败不覆写默认值。

## 5. 最终体验验收与性能门槛

### 5.1 必须实际完成的玩家操作

- 从出生点步行找到 NPC，用实际攻击输入击晕并搬走。
- 肩扛走楼梯、过自动门，分别完成直接上桌、存入池再取出、桌上直接调池库存三条路线。
- 人工完成一次全程画符，展示连续笔迹、跟随旋转和 100% 完成反馈。
- 加工中主动退出一次，由第二名玩家接手；再覆盖死亡、掉线与复活恢复。
- 等待真实 10 秒转化，领取药水、交接、送到法阵，金币正确增加 100；重复操作不重复领奖。
- 连续完成至少 3 轮，不重新启动服务器、不手动清理中间状态。
- 手机模拟器完成同一套核心操作；实体设备结果单独记录，不能用模拟器替代设备性能结论。

### 5.2 建议预算与边界场景

以下作为下一轮初始目标，需先测量基线；没有测量不得标注达标。

| 场景 | 初始目标 / 检查方式 |
| --- | --- |
| 普通桌面流程 | 稳定接近 60 FPS，记录帧时间尖峰及原因 |
| 约定的目标手机 | 至少稳定 30 FPS，必须明确机型与画质档位 |
| 满池、满架、多人加工 | 验证不持续物理抖动、不重复出货，记录实例与网络规模 |

| 中等延迟与丢包 | 校验本地反馈、权威结果、重复请求和交接，不凭主观描述“流畅” |
| 客户端晚加入或资源尚未复制 | 不访问缺失实例；收到材料 ID 后可恢复实体和笔迹 |

验收材料至少包括：静态检查结果、规则回归、实际操作步骤、关键截图或连续录像、性能记录，以及明确未通过/未验证项目。禁止把临时瞬移、直接改字段、孤立断言或自动扫涂包装为完整玩家验收。

## 6. 实施前需向用户确认的体验细节

| 待确认项 | 建议默认方向 | 影响 |
| --- | --- | --- |
| 白膜审美 | 保留无服饰、无复杂贴图，以比例、圆润程度和动作提升品质 | 决定模型、碰撞和笔迹表面的适配成本 |
